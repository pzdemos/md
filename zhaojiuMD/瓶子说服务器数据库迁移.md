  

  阶段一：生产转副本集（停服 1-2 分钟）

    选凌晨低峰执行
  1. 部署 keyFile（与之前测试环境一致）：


  echo "<KEYFILE_CONTENT>" > /opt/mongodb/keyfile
  chmod 400 /opt/mongodb/keyfile

  2. 停止当前 standalone mongod：


  killall mongod && sleep 3

  3. 以副本集模式重启（加 --oplogSize 10240 设 10GB oplog）：


  /mnt/db2/mongodb/mongodb-linux-x86_64-3.6.3/bin/mongod \
    --dbpath=/mnt/db2 --storageEngine wiredTiger --bind_ip 0.0.0.0 \
    --auth --replSet rs0 --keyFile /opt/mongodb/keyfile \
    --oplogSize 10240 \
    --logpath=/mnt/db2/mongolog/mongolog.log --fork

  4. 初始化为单成员副本集：


  rs.initiate({_id: "rs0", members: [{_id: 0, host: "<生产内网IP>:27017"}]})

  5. 验证：等待变为 PRIMARY，应用恢复正常 → 停服窗口结束

    此后生产以 rs0 PRIMARY 身份持续运行，oplog 
    开始积累。应用无感知（连接方式不变）。

  ────────────────────────────────────────

  阶段二：取快照（零影响，分钟级）

  6. 对生产数据盘 `d-m5e65vbwje5jbppkqv8s` 创建快照（通过 Aliyun API
     CreateSnapshot）
  7. 等待快照完成（3.5TB 盘通常 10-30 分钟）
  8. 记录快照 ID

    快照是增量的，对生产 IO 几乎无影响。

  ────────────────────────────────────────

  阶段三：准备高配 ECS 新数据盘

  9. 卸载高配 ECS 当前数据盘：umount /mnt/db2 → API DetachDisk
  10. 从新快照创建 ESSD PL1 磁盘（4000G，与原盘一致或更大）：API CreateDisk
     指定 SnapshotId + DiskCategory=cloud_essd + PerformanceLevel=PL1
  11. 挂载到高配 ECS：API AttachDisk → mount /dev/vdb1 /mnt/db2
  12. 验证数据文件完整：ls /mnt/db2/ 确认有 WiredTiger 文件和 shushubuyue 目录

    此时高配 ECS 的 /mnt/db2 与生产快照时刻的数据完全一致，包含 oplog。

  ────────────────────────────────────────

  阶段四：standalone compact（5-8 小时，完全独立）

  13. 以 standalone 模式启动（不加 --replSet，不影响生产）：


  /opt/mongodb/bin/mongod --dbpath=/mnt/db2 --storageEngine wiredTiger \
    --bind_ip 127.0.0.1 --auth \
    --logpath=/mnt/db2/mongolog/mongolog.log --fork

  14. 逐集合执行 compact（按大小从大到小，可随时中断恢复）：


  db.auth("mezizy", "<密码>");
  var sdb = db.getSiblingDB("shushubuyue");
  // 最大的先来，单个 2-3 小时
  db.adminCommand({compact: "shushubuyue.messages"});
  // 第二梯队，各 30-90 分钟
  db.adminCommand({compact: "shushubuyue.pairHistory"});
  db.adminCommand({compact: "shushubuyue.analytics"});
  db.adminCommand({compact: "shushubuyue.vipLog"});
  // 第三梯队，各 5-20 分钟
  db.adminCommand({compact: "shushubuyue.moderateLog"});
  db.adminCommand({compact: "shushubuyue.adConversation"});
  db.adminCommand({compact: "shushubuyue.dbOpLog1S"});
  db.adminCommand({compact: "shushubuyue.adTracking"});
  db.adminCommand({compact: "shushubuyue.adaReviewV2"});
  // ... 其余小集合

  15. 验证空间释放：df -h /mnt/db2 对比 compact 前后磁盘使用量

    整个阶段生产服务器零负载，两台机器完全独立运行。
  >
    即使 compact 花了 8 小时，生产 oplog 仅消耗 ~2 GB（10GB oplog 
    窗口绰绰有余）。

  ────────────────────────────────────────

  阶段五：加入副本集（分钟级）

  16. 停止 standalone mongod：


  killall mongod && sleep 3

  17. 以副本集模式启动：


  /opt/mongodb/bin/mongod --dbpath=/mnt/db2 --storageEngine wiredTiger \
  --bind_ip 0.0.0.0 --auth --replSet rs0 --keyFile /opt/mongodb/keyfile \
  --logpath=/mnt/db2/mongolog/mongolog.log --fork

    启动后，节点读取 local.system.replset 中的旧配置（只有生产 
    IP），发现自己不在成员列表中，进入非参与状态。但它知道 PRIMARY 
    的地址（生产内网 IP），可以与之通信。
  18. 在生产 PRIMARY 上添加为隐节点：


  rs.add({
    host: "<高配内网IP>:27017",
    hidden: true,
    priority: 0,
    votes: 0
  })

  19. 新节点行为：
    • 收到更新后的副本集配置，识别到自己
    • 检查本地 oplog 最后一条记录
    • 发现与 PRIMARY 的 oplog 重叠 → oplog 追赶（非 initial sync！）
    • 追赶 compact 期间积累的 5-8 小时 oplog（约 2GB 数据，几分钟完成）
  20. 监控追赶进度：


  rs.status()                      // 等待 stateStr: "SECONDARY"
  rs.printSlaveReplicationInfo()   // 延迟应快速降为 0


  ────────────────────────────────────────

  阶段六：切主

    确认高配节点为 SECONDARY 且延迟为 0 后执行
  21. 提升优先级：


  var cfg = rs.conf();
  cfg.members.forEach(function(m) {
    if (m.host.indexOf("<高配内网IP>") >= 0) {
      m.priority = 10;
      m.votes = 1;
      m.hidden = false;
    } else {
      m.priority = 1;
    }
  });
  rs.reconfig(cfg);

  22. 生产让位：


  rs.stepDown()  // 生产降为 SECONDARY，高配自动升 PRIMARY

  23. 验证：rs.status() 确认高配为 PRIMARY
  24. 修改应用连接字符串指向高配 IP
  25. 观察 24 小时确认业务正常


  ────────────────────────────────────────

  阶段七：善后

  26. 从副本集移除旧生产：rs.remove("<旧生产IP>:27017")
  27. 旧生产改回 standalone 作冷备，或关停
  28. 释放替身 ECS（i-m5e69jniz6nvhoegcwq7）
  29. 高配 ECS 转包年包月

IP 迁移步骤（切主之后）

  在高配成为 PRIMARY 且验证业务正常后执行：
  Step 1：生产 IP 转为 EIP

  API: ConvertNatPublicIpToEip
  InstanceId: i-m5e94ugtbu9qsebxtibn

    47.104.58.237 从固定 IP 变为 EIP，仍绑在生产服务器上，业务不中断。
  Step 2：释放高配的固定公网 IP

  API: ModifyInstanceNetworkSpec
  InstanceId: i-m5ebzampnxdkm8pgyqqr
  InternetMaxBandwidthOut: 0

    120.27.123.101 被释放，高配暂时无公网 IP。此时 MongoDB 已通过内网 IP 
    提供副本集服务，不影响数据同步。
  Step 3：解绑 EIP 并绑到高配（短暂停服 ~1 分钟）

  API: UnassociateEipAddress    ← 从生产解绑 47.104.58.237
  API: AssociateEipAddress      ← 绑到高配 i-m5ebzampnxdkm8pgyqqr

    这 1 分钟内 47.104.58.237 不指向任何服务器，应用连接会短暂中断。
  Step 4：验证
  应用通过 47.104.58.237 连接到高配新 PRIMARY，恢复正常。
